## Issues Found

1. **NOTED (non-blocking, pre-existing, out of scope):** `specclaw-verify`'s `cmd_collect` has a confirmed bug in its `Files:` line parser — its fallback comma-split logic is gated on the *global* file-paths array being empty rather than whether the *current* task's line matched, so once one task's `Files:` line populates the array via fallback, every subsequent task's `Files:` line is silently dropped. This caused the verify-context payload's "Implementation (changed files)" section to show only 1 of ~14 actual changed files for this change. It was already flagged by a prior verify pass on `analyze-command` (see `.specclaw/changes/analyze-command/verify-report.md` Issues #4) as pre-existing and unrelated to that change; it is equally pre-existing and unrelated to `architecture-command` — not fixed here, flagged again for the operator's continued awareness since it surfaced again during this verification. To work around it, every file in scope was independently Read directly from the working tree rather than relying on the payload's (incomplete) file list.

2. **Minor fixture-layout deviation from spec/design/tasks' illustrative example (harmless).** AC5, design.md's Risks section, and tasks.md's T5 notes all describe the `.csproj` fixture's `ProjectReference` path as `"../Other/Other.csproj"`. The shipped fixture instead has `App.csproj` at the fixture root referencing `<ProjectReference Include="Other/Other.csproj" />` (no `../`) — correct, since `Other/` is a child directory of the fixture root where `App.csproj` also lives, so `../` would actually be the wrong relative path for that layout. This is a sensible implementation choice that diverges from the spec text's literal example without violating its substance (AC5's actual requirement — an edge with `kind: project_reference` to the referenced path, and no leak into the manifest's own `dependencies` — is fully satisfied and tested). No fix needed; flagging only because the task asked to note deviations from design.md even when harmless.

3. **Design.md's own self-identified highest risk (FR9.3 / AC13's migration step) remains untested by the automated suite**, as design.md's Risks & Mitigations section itself acknowledges: "The one-time old-path migration (FR9.3) is new logic in what's otherwise a mechanical relocation, and is the one piece of this change most likely to be under-tested." This is structurally true — the migration logic lives in a Markdown skill file's Bash instructions, not in the bash *script* `run-parser-tests.sh` exercises, so the existing parser-test harness has no natural way to assert it. **Suggested fix (non-blocking):** either add a small standalone shell test that stages an old-path `codebase-report.md`, extracts and runs Step 2's two commands verbatim, and asserts the archive result — or accept this as an intentionally manual/agent-verified behavior given the harness's current scope (bash-script parser tests, not skill-orchestration tests).

4. **Several spec.md Edge Cases are not directly exercised by a dedicated test** (noted inline above where applicable): (a) a genuinely multi-line Delphi `uses` clause (the fixture's `UnitA.pas` clause is single-line); (b) case-differing Delphi unit reference (fixture uses exact-case `UnitB`); (c) a true circular edge (A→B and B→A) in any of the three ecosystems; (d) a repo/scope with **zero** dependency-graph-eligible files of *any* kind (only the Go-specific "zero contribution" case is tested via `go.mod`); (e) reports existing at both old and new `codebase-report.md` paths simultaneously; (f) a true multi-ecosystem monorepo scoped to one subproject (only a single-ecosystem, single-subdir scoping case is tested). None of these appear to be broken by code inspection (the `awk` state machine is bounded-block by design, case-folding is explicit in `resolve_unit_to_scoped_file`, `dependency_graph` is a flat non-traversing list so cycles can't hang it, and every extraction loop is gated on `$tmp_scoped` so an all-ineligible scope naturally yields `[]`) — but none of these six edge cases has a fixture-backed assertion proving it. **Suggested fix (non-blocking):** low priority given the shallow-v1 scope already stated in spec.md's Notes section, but worth a follow-up test-coverage pass if `dependency_graph` sees further investment.
